## The eight candidates

### 1. Run record gaps (`cns.run/1`): ACCEPT, additive

Evidence. WATCHER_MCU 0.3.6 keeps a real record, `tests/fixtures/warden_0_13_6_declined_record.json`: decision
`FINISH_REJECTED`, `converged: true`, `unmeasured: []`, `finished: false`, and `ghost_scan.declined` listing seven
checks (`mutate`, `kernel`, `structure`, `tests`, `project`, `secrets`, `correlate`). The Watcher fixed its own
narration in 0.3.6; CNS still gives a reader no field for any of it. `RunRecord` has no `declined`, nothing that
collects the `dirty` flags scattered over `versions.*`, no `reobserved`, and nothing that says what "converged"
means beside a count of findings. JUDGE 0.4.8 (`judge/seat.py`) states in its docstring that its cycle check
"cannot fire when a finisher may have run" and that closing it "needs a `finisher ran` field in the CNS Evidence
shape, which is a change to CNS and the owner's call".

Decision. `cns.run/1` stays. No field loses or changes meaning, so `run/2` is not needed; everything is a field
with a default or a pure function of the row:

- `RunRecord.reobserved` (finding identities at the end), `RunRecord.declined` (read from `ghost_scan.declined`,
  which must be a list of text when present), `RunRecord.swizzle_sound`.
- `RunRecord.gaps()`: every reason the run is less than fully measured, in words: each `unmeasured` entry, each
  declined check, each `ghost_scan.gaps` entry, each part of `versions` flagged `dirty`. A record with
  `unmeasured: []` and seven declined checks has seven gaps, and a narrator that says "gaps: none" is wrong by
  this function.
- `RunRecord.participants()`: (name, commit, dirty) for Warden, each instrument, each seat and each join, the
  commit set the run actually used. `RunRecord.dirty_parts()` is the subset flagged dirty.
- `RunRecord.findings_remaining` and `RunRecord.clean`: converged means no proposals were left, and `clean` is the
  stronger claim (ACCEPT, converged, nothing put back, no gaps, no findings remaining).
- `cns.seat.Evidence.finisher_ran: Optional[bool] = None`: None is "not said", as every other unmeasured value in
  that row.

Consumers. WATCHER_MCU reads `RunRecord` (unchanged fields still read). WARDEN writes the record and the
`Evidence` (it may fill `finisher_ran`; nothing breaks if it does not). JUDGE reads `Evidence` by `getattr` and may
close its known limit once Warden fills the field. BURNISH and DRAFTER read `Facts` and `FileEdit`, untouched.

### 2. Manifest and install-file drift: ACCEPT, non-breaking

Evidence. `contracts/warden-stack.json` is written by `repin` and by hand; `contracts/install-stack.txt` is
written by hand only, and the history shows six commits whose purpose was to bring the second back in line with
the first (`d318ee6`, `ca0daaa`, `fcb7f3e`, `3e6c257`, `f5dd52a`, `71db25a`). `tests/test_install_stack.py` holds
the seven commits equal but nothing regenerates the file.

Decision. One source of truth: the manifest, the release table and the lines a person owns (the header comment,
the watcher-mcu pin, the version comments). `cns_composition.install_stack` renders the install file from those and
checks the committed file is that rendering; `repin` re-renders it when it moves a pin, so the two files cannot
drift by one tool and not the other; the repin workflow's proposal carries both files and re-checks the rendering;
the stack workflow checks each version comment against the distribution it installed. Full 40-hex commits are
required by the renderer, by the workflow checkout step (already) and, if accepted below, by `cns.stack` itself.
Manifest coverage: `repin --check` and `seat_pins` name any stack folder the manifest does not cover, as a note,
because Warden 0.13.8 refuses only a folder it uses (WATCHER_MCU sits in the stack and is not used by Warden).

### 4. Packaging: ACCEPT the boundary; DEFER the name to the owner

Decision on the boundary. The maintenance tools (`repin`, `seat_pins`, `cns_versions`, `install_stack`,
`circuit_canary`, `circuit_refusals`, `link_ledger`, `consumers`, `digest_vectors`) need `contracts/`, which is
state and stays outside the wheel (the README rule: "a pin is state and the package holds none"; Warden's `--cns`
reads the same folder from a checkout path). An installed wheel therefore cannot run them with their defaults. 2.0.0
says so and tests it: each tool exits 2 with "run from a CNS checkout" when `contracts/` is not beside the package,
instead of a traceback or a misleading "0 repositories". Shipping `contracts/` as package data is rejected.

Decision on the name, for the owner. `pip install cns` installs an unrelated project (2.3.50 on PyPI). No consumer
installs CNS by name (every pin is a direct git URL, and pip refuses to mix a direct URL with an index release), so
the collision bites only a person typing the name, and a future resolver run where any package in the environment
depends on `cns` from the index. The option: rename the distribution to `cns-contracts` and keep the import name
`cns`. What changes: `name` in `pyproject.toml`; the dependency line in all eight circuit repositories and in every
other consumer the ledger lists (37 two-way); `contracts/install-stack.txt`; the `cns` regexes in `seat_pins`,
`cns_versions`, `link_ledger` and `tests/test_install_stack.py`; the one-distribution check in `stack.yml`. A
consumer that keeps `cns @ ...@v1.9.0` keeps working; a consumer that moves to `@v2.0.0` must move the name in
the same edit or pip reports "requested cns but got cns-contracts". Recommendation: do it at 2.0.0, because this
is the one release at which every consumer edits its pin line anyway, and a rename later costs the same
coordinated move a second time. It is not implemented here; it is one more labelled commit if the owner says yes.

### 5. Pin policy as code: ACCEPT, non-breaking

Evidence. `seat_pins` compares pin text across repositories but does not read `contracts/install-stack.txt`, so
the install file can spell `Warden.git` where a repository spells `WARDEN.git` and nothing says so until pip does.
`consumers.drift`, `digest_vectors.drift` and `link_ledger._folder` each skip a stack folder that is a symlink
(`not p.is_symlink()`), while `repin`, `seat_pins` and `cns_versions` follow one since `df27f45`; the same stack
folder gives two tools two different repository sets. The tag spelling for the CNS pin is a policy stated in a
comment and held only by `test_install_stack.py` for the install file.

Decision. `seat_pins` reads the install file as one more member of the agreement and reports a spelling difference
by normalised URL; `cns_versions --spelling tag` fails a CNS pin spelled as a commit, used by the stack workflow for
the circuit repositories (the links workflow keeps the default, because Link pins a commit on purpose and the
table records it); `consumers`, `digest_vectors` and `link_ledger` use `repin.stack_folders` so every tool sees the
same folders.

### 6. Robustness class: ACCEPT

Evidence, reproduced on the base commit. With file descriptor 1 closed (`>&-`), all seven CLIs exit 0 and print
nothing: Python sets `sys.stdout` to `None` and `print` becomes a no-op, so a report that was never delivered reads
as success. A reader that closes the pipe before the summary is written ends in `BrokenPipeError` at interpreter
shutdown. `repin` and `digest_vectors --write` write the file in place with `write_text`, which truncates first,
follows a symbolic link, and blocks forever on a named pipe. `repin`'s dirty check runs `git status` under the
user's configuration and does not look at index flags, so a seat file modified then marked `assume-unchanged` is
pinned as clean, the bypass Warden 0.13.8 closed.

Decision. One helper, `cns_composition.delivery`, that every CLI ends with: a report that cannot be delivered
(closed stdout, broken pipe, a full device reported by `OSError`) is said on stderr and the exit is 2, never 0; a
file written by a tool goes to a temporary name in the same folder and is renamed into place only when the
destination is absent or a regular file, and a symbolic link, named pipe, device or folder at the destination is
refused by name; `repin` asks git the way Warden 0.13.8 does (no user or system configuration, every untracked
file counted, index flags refused). Tests use only a closed descriptor, a pipe whose reader has gone, a FIFO and
folders the test creates, and a stand-in stream that raises `ENOSPC`; no device node is written to.

### 7. Release process as code: ACCEPT

Evidence. The version lives in `pyproject.toml` and `cns/__version__`; the README's "Released tags" sentence and
its consumer examples carry it again; `contracts/cns-releases.json` carries `current` and `floor`; there is no
CHANGELOG. The README showed `@v1.0.0` for a month (`9f29b76` fixed it) and the installed tag lacked tooling
that the tree had for five days.

Definitions, so the words have one meaning:

- `current` is the newest release that is tagged. It moves when a tag exists, never before. Between a version
  bump and its tag the package version is ahead of `current`, and that is the only state in which they may differ.
- `floor` is the lowest release a consumer may pin; `cns_versions` fails a pin below it. Raising the floor to a
  version forces every consumer below it to move. The floor never exceeds `current`.
- The tag text is `v` + the package version, and the tag's commit declares that version in `cns/__init__.py`.

Decision. `cns_composition.release --check` holds all of them together (package version, `__version__`, the
CHANGELOG's top entry, the README's tag list and examples, the table's `current` and `floor`, the install file's
CNS pin) and `tests/test_release.py` runs it on every suite run. `release --record vX.Y.Z` is what the owner runs
after tagging: it peels the tag in the local checkout, reads the version at that commit, adds the row, moves
`current`, and rewrites the README's examples. The floor stays 1.9.0 in 2.0.0 (DEFER the raise): raising it to
2.0.0 before the eight repositories re-pin would turn the links and stack workflows red for every one of them at
once; the follow-up that re-pins them raises it.

### 8. Honest docs: ACCEPT

The README gains "What works", "What does not work", "What broke and how it was fixed" (a ledger built from the git
log and the sibling changelogs, each row naming the commit), and "Ceilings code cannot fix": repositories weeks old,

## Breaking items, waiting for approval

### B1. `cns.stack`: a pin is exactly 40 lowercase hex characters, and `pins()` no longer matches a prefix

Approved by the owner on 2026-10-22 (see "The owner's decisions, 2026-10-22"). Commit `f46f77f` stays.

Today `StackPin.problems()` accepts 7 to 40 characters and `StackPin.pins()` matches a 7+ character prefix. Warden
has refused anything but a full commit since 0.13.7, the stack workflow's checkout step refuses it, and
`test_the_circuits_manifest_beside_the_package_satisfies_the_shape` already asserts 40. The shape says one thing and
every reader of it enforces another. Under the README's rule a field given a new meaning is a major version, and
this gives `commit` a narrower meaning and removes the prefix behaviour of `pins()`.

Who it breaks. None of the eight circuit repositories imports `cns.stack` (measured with `consumers.scan` on the
pinned checkouts: Warden reads the manifest JSON itself). Inside CNS: `repin` (which validates with the shape),
`tests/test_stack.py` (one test asserts the prefix behaviour and is updated under rule 5). A hand-written manifest
with a short pin becomes invalid to CNS as it already is to Warden. Migration note for consumers: none needed.

### B2. Distribution name (see candidate 4): the owner's call, not implemented

Deferred by the owner on 2026-10-22, with the reasons recorded under "The owner's decisions, 2026-10-22". Still not
implemented.

### B3. Floor raise to 2.0.0: recommended against for this release (see candidate 7)

## The owner's decisions, 2026-10-22

Made after the candidate was built and tested. They change what ships and what does not; nothing above is
rewritten, so the evidence for each option stays readable.

1. **B1 stays; the version is 2.0.0.** Commit `f46f77f` ("StackPin requires 40 lowercase hex") is kept. It is the
   one change that narrows what a field means, and by the README's rule that is a major version. No circuit
   repository imports `cns.stack`, so no consumer edits code for it.
2. **The distribution rename to `cns-contracts` is deferred, and not implemented.** The reasons, so the question is
   not re-opened from nothing:
   - Every pin and every document in the circuit uses a git URL. pip does not mix a direct URL with an index
     release, so the collision with the unrelated `cns` on PyPI (2.3.50) bites only a person who types a bare
     `pip install cns`, or a resolver run in an environment where some other package depends on `cns` from the
     index. Neither is a current consumer.
   - The rename is itself a breaking change: the dependency line in all eight circuit repositories, in the other
     consumers the ledger lists, in `contracts/install-stack.txt`, in three tools' regexes and in the
     one-distribution check would move together, and a consumer that moves to `@v2.0.0` would have to move the name
     in the same edit.
   - Because it is breaking, it should be decided before outside users arrive, when it costs one coordinated
     edit across repositories with one maintainer. After that it costs every outside user an edit. Nothing in this
     release makes that later move harder; the import name stays `cns` either way.
3. **The final consumer pass is small on purpose.** Re-pin all eight repositories to `@v2.0.0`, and have Warden
   fill the new `Evidence.finisher_ran` field. Nothing else in 2.0.0 is adopted in that pass: JUDGE's adoption of
   `finisher_ran` (the field its own docstring names as the one that would close its known limit) and WATCHER_MCU's
   adoption of `RunRecord.gaps()` and `clean` are deferred to later passes, each its own change in its own repository.

## Version recommendation

2.0.0 if B1 is accepted (with or without B2). B1 is a real contract change by the repository's own rule, small in
blast radius and already the behaviour of every reader. If B1 is dropped, nothing in the shapes or the documented
contract breaks, and the release is 1.10.0: every other change is a field with a default, a pure function of a row,
or behaviour beside the package.

## Rejected

- A `cns.run/2` schema: no existing field changes meaning, so a reader of run/1 keeps reading.
- Folding declined checks into `unmeasured`: that would change the meaning of a field Warden writes and the Watcher
  reads; `gaps()` reads both as they are.
- Shipping `contracts/` in the wheel: a pin is state; the checkout boundary is documented and tested instead.
- Adding `cycles` to `RunRecord`: `test_extra_keys_are_allowed_and_ignored` asserts it is ignored and nothing in
  this release needs it; `reobserved` carries the end state.
- A second workflow job for the refusals: one more step in the one `stack` job keeps the workflow's one-job tests
  and puts the red where the positive canary is.

## Findings while implementing

- `seat_pins --install contracts/install-stack.txt` on the pinned stack reports a disagreement the base commit
  could not see: WARDEN's `ghost` extra pins ghost-tools at `c2ada82d2f6c0404074a668ba749c7872743aad9` while the
  install file installs `2d03d8e19dc5937a6f45379c429d1a3afce4ab29`. `pip check` passed because the extra is not
  installed. Warden 0.13.8 moved that pin to `2d03d8e`, so this closes with the same re-pin that closes the four
  red refusal cases. Until then the `stack` job's seat_pins step is red, and that is the finding.
- `circuit_refusals` on throwaway clones, measured serially (the sandbox saturates under two circuit runs at once):
  Warden 0.13.7 refused 5 of the 9 fast cases (dirty tracked, dirty untracked, short, uppercase, wrong commit) and
  ran on for the omitted seat and the three git hides; Warden 0.13.8 refused all 9. The red-suite case needs a
  full run and is proven in CI only (the `unshare` limit above).
- The suite creates about 40,000 small files per run under pytest's basetemp (git repositories in fixtures), which
  exhausted this sandbox's `/tmp` metadata while bytes were still free; `--basetemp` under scratch avoids it. Not a
  defect in the tree, noted so the next person does not chase it.
- **The delivery guard did not hold with unbuffered stdout.** Found after the candidate's own CI was green, by
  running the suite on a machine that sets `PYTHONUNBUFFERED=1`: three tests in
  `cns_composition/tests/test_delivery.py` (`consumers`, `digest_vectors`, `link_ledger`, reader gone) failed with a
  raw `BrokenPipeError` traceback and exit 1. Every command ended with `return delivery.deliver(_main(argv), name)`,
  so `_main` ran, and printed, before `deliver` could protect it. With buffered stdout (the default, and a CI
  runner's) a print only fills a buffer and the failure shows at the flush that `deliver` makes, which is why CI
  never saw it. With unbuffered stdout each print is a write and raised out of `_main` directly: a closed pipe gave
  `BrokenPipeError` and a full device gave `OSError` (ENOSPC), exit 1 with a traceback, for all ten commands. A
  closed descriptor 1 was never affected (`sys.stdout` is None and `print` is a no-op). It also meant a lost first
  print ended the command before the work after it. Fixed by `delivery.run`, which guards stdout while `main` runs
  (the first write error is kept and later writes dropped, so the work is finished and the command's own code kept)
  and then handles the loss as `deliver` always did. The tests now run each of the ten commands in both buffering
  modes, set explicitly in the child's environment, for a gone reader, a closed descriptor 1 and a full device.
