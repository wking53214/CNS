# Runbook: moving the STACK library to CNS v3.0.0

Status: in progress. Written 2026-11-11, after CNS v3.0.0 was recorded on main (pull request 135).
This runbook is for the mechanical pass. Anything it says to escalate is for a stronger review pass.

## The gate (already met)

- `contracts/cns-releases.json` names v3.0.0 as current.
- `contracts/install-stack.txt` names `CNS.git@v3.0.0`.
- The spine repositories (alpha, zeta, beta, delta) are on main at the heads in `contracts/spine-manifest.json`.

Do not start a repository until the gate still holds on the day you start. Check with
`git fetch origin main` in CNS and read those two files.

## Order

Move repositories in this order. A repository's Warden or ghost_tools pin must not point at a
commit that is older than the pin of a repository upstream of it.

1. Circuit: `ghost_tools`, `SWIZZLE`, `ASSAY`, then `WARDEN`, then `JUDGE`, `BURNISH`, `DRAFTER`, `WATCHER_MCU`.
2. Everything else, including `UAI-2` (run its tests first; it is the impact test for the fingerprint rule).
3. CNS itself last: re-pin with `python -m cns_composition.repin` only after every repository above has a merged pull request.

## Per repository

1. **Read the head.** `git fetch origin main`, then work on a new branch from `origin/main`.
   If a pull request for this change is already open, stop and log it. Do not open a second one.
2. **Find every CNS pin.** Look in `pyproject.toml`, `setup.cfg`, `requirements*.txt` (also in subfolders), and
   `.github/workflows/*.yml`. A pin looks like `CNS.git@v2.3.0`, `CNS.git@v2.4.0`, or `cns @ ... CNS.git@<sha>`.
   Also note any other STACK pins the file states: `Warden.git@`, `ghost_tools`, `JUDGE.git@`, `ASSAY.git@`,
   `SWIZZLE.git@`, `interconnected_*@`. Record every hit in your log.
3. **Change only the pin strings and the assertion that checks each one.** Some repositories have a test that
   asserts their pin (for example `tests/test_cns_independence.py`). Update that assertion to the new value and
   nothing else in it. Do not edit any other test.
4. **Update docs that state the pin.** The README, STACK.md, CHANGELOG pin lines, and any "pinned to" comment.
   Use the same new value. Do not rewrite prose.
5. **Run the suite before you open the pull request.** Install the new pin, then run the repository's own test
   command (read its CI workflow for the exact command). Record the exact pass and fail counts.
6. **Open one pull request** from the branch, into main, with the pin change, the docs, the test counts, and
   what was not tested. Do not merge it.
7. **Log the result** in the sweep log: repository, pull request number, pass and fail counts, and any escalation.

## Stop and escalate (do not fix)

Stop and record the repository as ESCALATED, with the failing test name and the first error line, when:

- The suite fails after the pin change. Do not edit code to make it pass. Do not skip, disable or quarantine any test.
- The Warden, ghost_tools or JUDGE pin in the repository disagrees with the circuit heads on main.
- The repository has an open pull request or a branch that already changes its pins.
- The repository is archived. Archived repositories are out of scope until the owner says otherwise.
- The repository has no CI workflow and no test command you can find.
- A pin you need to change is in a file this runbook does not list. Log the file and stop.

## Rules that do not bend

- No merges. Every pull request waits for the owner.
- No force-push, no branch deletion, no changes to a repository's default branch.
- BURNISH: a change may not sit under "Unreleased" in its changelog (a test enforces it). Make it a version bump
  and update the version in its package file, pyproject, README and changelog, the way its previous pin move did.
- No model or tool names in commit messages or pull request bodies beyond the attribution lines.
- Do not use em dashes in any text you write.

## Done means

A repository is done when all of these are true on its pull request:

- Every CNS pin in its dependency files and workflows names v3.0.0 (or the spine commit it is pinned to).
- Its docs state the same values.
- Its own suite passed with the new pin, and the counts are recorded.

The library is done only when a fresh scan of every active repository finds no CNS pin below v3.0.0,
and every remaining pin that the scan lists is either merged or logged as ESCALATED. Until that scan
is clean, the status is "in progress".
